# 200-Day MA Tracker

Tracks the 200-day simple moving average (SMA) of ETFs such as QQQ and SPY, shows the result on a static web page, and sends a Telegram alert when the regular-session close crosses the 200 MA.

- **Data source:** [Tiingo](https://www.tiingo.com) end-of-day prices (free tier)
- **Scheduler and compute:** GitHub Actions (free)
- **Hosting:** Cloudflare Pages (static page); GitHub Pages also works
- **Alerts:** Telegram bot

## How it works

```
GitHub Actions (cron, weekdays after the US close)
  -> scripts/update.mjs
       fetch Tiingo daily prices
       compute 200 SMA
       detect a cross (today's close vs. yesterday's close, each against its own 200 SMA)
       send a Telegram alert if crossed (once per bar date per ticker)
       write docs/data/latest.json
  -> commit docs/data/latest.json to the repo
  -> deploy the docs/ folder to Cloudflare Pages
```

The website is fully static. It loads `data/latest.json` in the browser and draws the chart. Nothing is calculated when someone visits.

## Repository layout

```
.github/workflows/update.yml   schedule, ticker list, deploy steps
scripts/update.mjs             fetch data, compute MA, alert, write JSON
docs/index.html                the web page (Pico.css + Chart.js)
docs/data/latest.json          generated by the script; do not edit by hand
README.md
```

## Setup

### 1. Get your keys

| Secret | Where to get it |
|---|---|
| `TIINGO_TOKEN` | Tiingo account page, API section |
| `TELEGRAM_BOT_TOKEN` | Message @BotFather in Telegram, send `/newbot` |
| `TELEGRAM_CHAT_ID` | Send any message to your bot, then open `https://api.telegram.org/bot<TOKEN>/getUpdates` and copy `message.chat.id` |
| `CLOUDFLARE_API_TOKEN` | Cloudflare dashboard, My Profile, API Tokens, custom token with **Account > Cloudflare Pages > Edit** |
| `CLOUDFLARE_ACCOUNT_ID` | Cloudflare dashboard, Workers & Pages overview (right sidebar) |

### 2. Add the secrets

In the GitHub repo: **Settings > Secrets and variables > Actions > New repository secret**. Add all five names exactly as shown above.

Also check **Settings > Actions > General > Workflow permissions** is set to **Read and write permissions**.

### 3. Create the Cloudflare Pages project (once)

Create a Pages project with direct upload (not Git-connected) and set its name to match `--project-name` in `update.yml`. If the name you want is taken, Cloudflare adds a suffix, and the workflow must use the exact final name.

### 4. First run

Go to **Actions > Update 200MA > Run workflow** (tick the test option to send a test Telegram message). A green run creates `docs/data/latest.json` and deploys the page.

## Changing tickers

The only place to edit is the `SYMBOLS` line in `.github/workflows/update.yml`:

```yaml
- name: Fetch data, compute MA, send alerts
  run: node scripts/update.mjs
  env:
    SYMBOLS: "QQQ,SPY"        # change this, e.g. "QQQ,SPY,IWM,DIA"
```

1. Edit the list, comma-separated.
2. Commit the change.
3. Run **Actions > Update 200MA > Run workflow** to apply it immediately.

Each ticker gets its own tab on the page automatically. `update.mjs` and `index.html` need no changes.

Notes:

- Use tickers Tiingo covers. US stocks and ETFs work. Index symbols like `^GSPC` usually do not, so use an ETF such as SPY or VOO.
- A ticker that fails does not block the others; the run is marked red so you notice.
- A newly added ticker does not trigger a flood of alerts. It alerts only when its state changes versus the previous bar.
- **Removing a ticker:** deleting it from `SYMBOLS` stops updates, but its old data stays in `latest.json` and its tab remains. To remove it fully, delete `docs/data/latest.json` and re-run the workflow. The file is rebuilt with only the current list.

## Changing the schedule

In `.github/workflows/update.yml`:

```yaml
schedule:
  - cron: "30 21 * * 1-5"
  - cron: "30 22 * * 1-5"
```

- Cron times are in **UTC**. Format: `minute hour day-of-month month day-of-week`.
- The US regular session closes at 16:00 New York time, which is 20:00 UTC in summer (EDT) and 21:00 UTC in winter (EST). The runs are set after both, so they work all year.
- The second run is a retry in case the data was late. Duplicate alerts are prevented.
- GitHub may delay scheduled runs by several minutes, and occasionally skips one.
- Do not schedule a run before the close.

## Changing the appearance

Edit `docs/index.html`:

- Colors for status and chart lines: the `--up`, `--down`, `--line`, `--ma` variables at the top of the `<style>` block.
- Page text, title, and footer: the HTML in `<body>` and the `init()` function.
- Cards shown: the template inside `show()`.

After editing, commit and run the workflow once so the Cloudflare deploy publishes the change.

## Alert logic

For each ticker, the state is `above` if close > 200 SMA, otherwise `below`. An alert is sent when the latest bar's state differs from the previous bar's state. The last alerted bar date is stored per ticker in `latest.json`, so the retry run cannot send a duplicate.

The script uses the raw `close` field (regular-session close, not dividend-adjusted). To use dividend-adjusted prices, change `b.close` to `b.adjClose` in `update.mjs`.

## Troubleshooting

| Symptom | What to check |
|---|---|
| No scheduled runs appear | Workflow must be on `main`; look for a "workflows disabled" banner in the Actions tab; check the YAML for errors |
| `TIINGO_TOKEN is not set` | Secret missing or misnamed (case-sensitive) |
| `Tiingo HTTP 401/403` | Wrong token, or stray space/newline in the secret |
| `Telegram HTTP 400/404` | Wrong bot token or chat ID, or you have not messaged the bot yet |
| Push fails with 403 | Set workflow permissions to Read and write |
| Cloudflare deploy auth error | Token needs **Cloudflare Pages: Edit**; check the account ID |
| Deploy says project not found | `--project-name` must match the Cloudflare project name exactly |
| Fetch step says `No changes` | Normal on weekends, holidays, or before the new bar is published |
| Page looks stale | Hard-refresh (Ctrl+Shift+R); check the close date on the cards |

## Maintenance

Normally none. Things that can break it over time:

- Tiingo changes its free tier or API.
- Your Cloudflare API token expires (update the secret).
- GitHub pauses schedules after 60 days without repo activity. Daily data commits usually prevent this; if it happens, re-enable the workflow in the Actions tab.
- Action versions become outdated (`actions/checkout`, `actions/setup-node`, `cloudflare/wrangler-action`). Update the version numbers when deprecation warnings become errors.

## Privacy

The repo is public by default, so code, data, and run logs are visible. API keys are stored only in GitHub Secrets and are never written to files or logs. To hide the code and data, make the repo private; the Action and the Cloudflare site keep working. To restrict the site itself, put the Cloudflare Pages project behind Cloudflare Access.
